# Contributing

Thank you for your interest in this project. It began as a personal tool and is maintained on a best-effort basis, but contributions, bug reports and suggestions are genuinely welcome.

## Before you start

For anything beyond a trivial fix (typos, small copy changes), please open an issue first to discuss the change. This avoids wasted effort on a pull request that does not fit the project's direction.

## Development setup

Follow the [Setup](README.md#setup) and [Development](README.md#development) sections of the README. You will need your own Supabase project to run the app end-to-end; the bundled fallback question set lets you exercise most of the UI without one.

## Branching and commits

- Branch from `main`.
- Use a short, descriptive branch name, e.g. `fix/weak-spots-due-filter`.
- Write commit messages in the imperative mood ("Fix", not "Fixed" or "Fixes"), and explain *why* a change was made when the reason is not obvious from the diff itself.
- Keep commits focused. A pull request that mixes an unrelated refactor with a bug fix is harder to review and harder to revert if something goes wrong.

## Code style

- Match the existing style of the file you are editing rather than introducing a new convention.
- Avoid adding new dependencies unless there is a clear need; this app deliberately keeps its dependency surface small.
- Do not add comments that restate what the code does. Comments should explain a non-obvious constraint, trade-off or workaround.
- Do not commit generated or native build output. The `android/` directory is generated by `expo prebuild` and is intentionally not tracked.

## Security-sensitive changes

Anything touching authentication, the Supabase client configuration, environment variable handling, or the sync/offline cache in `src/db.js` should be treated as security-sensitive. In particular:

- Never commit a `.env` file, an API key, or any other secret.
- Never widen a database permission or Row Level Security policy without explaining why in the pull request description.
- If you believe you have found a vulnerability rather than a bug, please follow [SECURITY.md](SECURITY.md) instead of opening a public issue.

## Testing before submitting

There is no automated test suite for this project yet. At minimum, before opening a pull request:

- Run the app on a physical device or emulator and exercise the affected screens.
- Confirm `npm audit` and `npx expo-doctor` report no new issues.
- If your change touches the offline cache or sync queue, test with the device offline as well as online.

## Pull requests

- Describe what changed and why, not just what.
- Link the issue it resolves, if any.
- Note any manual testing you performed, including on which Android version/device.

## Reporting bugs

Please use the bug report issue template and include:

- Steps to reproduce
- What you expected to happen
- What actually happened
- Android version and device model
- Whether the app was online or offline at the time
